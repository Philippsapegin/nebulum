# P2P mesh-чат (тестовый проект для будущей игры)

Прототип полностью децентрализованного чата между браузерами: WebRTC DataChannel,
ручной сигналинг (копипаст кодов), без сервера и без зависимостей.
Цель — отработать принципы P2P перед разработкой браузерной игры (mesh, 2–4 игрока).

## Текущее состояние

- **Один файл** `index.html`: vanilla JS + CSS, никаких фреймворков и build-шага.
- **Задеплоено:** https://p2p-chat.pavel-tarasov.workers.dev/ (Cloudflare Workers,
  static assets, drag&drop через дашборд; обновление — кнопка New deployment).
- **Проверено:** работает в локальной сети (телефон↔ПК) и через интернет
  Израиль↔Россия — прямое UDP-соединение srflx↔srflx, без релея.
- **Передача файлов:** текстовые файлы (например, JSON ~1 МБ) — кнопка «Отправить
  файл» рядом с чатом, лимит 5 МБ. Идёт по тому же DataChannel, без сервера.

## Архитектура

- Топология — full mesh: отдельный `RTCPeerConnection` + `RTCDataChannel` на каждую
  пару. N участников = N×(N−1)/2 ручных рукопожатий.
- Роли на этапе установки: инициатор («Создать приглашение»: `createDataChannel` →
  `createOffer`) и принимающий («Принять приглашение»: `setRemoteDescription` →
  `createAnswer`; канал получает через `pc.ondatachannel`). После открытия канал
  симметричный.
- **Vanilla ICE:** ждём `iceGatheringState === "complete"` (+ таймаут 3с), затем
  весь `localDescription` кодируется в одну строку: `btoa(JSON.stringify(desc))`.
- Broadcast = цикл `send()` по всем открытым каналам. Релея/пересылки между пирами нет.
- Сообщения — JSON `{from, text}`; имя отправителя берётся из поля «Ваше имя».
- **Передача файлов** поверх того же канала, свой мини-протокол сообщений:
  файл читается как `ArrayBuffer` → кодируется в base64 → режется на чанки по
  16 КБ (лимит на один DataChannel-message) → шлётся как `file-meta` →
  N×`file-chunk` → `file-end`, каждому открытому пиру отдельно (без релея).
  Приёмник копит чанки в массив по `id` и собирает `Blob` на `file-end`;
  ссылка на скачивание рендерится в чате. Бэкпрешер — ждём событие
  `bufferedamountlow`, если `channel.bufferedAmount` превысил порог (1 МБ),
  прежде чем слать следующий чанк. Лимит размера файла — 5 МБ (safety cap).
- STUN: только `stun:stun.l.google.com:19302`.
- Шифрование: DTLS встроено в WebRTC всегда, ничего делать не нужно.

## Ключевые структуры в коде

- `peers[]` — список `{ id, label, pc, channel, role, ui, incomingFiles }`.
  `incomingFiles` — буфер входящих файлов по `id`, пока все чанки не собраны.
- `RTC_CONFIG` — конфиг ICE-серверов (константа вверху скрипта).
- UI-карточки соединений генерируются в JS (`startInvite` / `startAccept`).
- `sendFile` / `attachChannel` (обработка `file-*` типов) — вся логика передачи файлов.

## Известные проблемы / выводы из тестов

1. **Сбор ICE-кандидатов — самое хрупкое звено.** Был случай: STUN не ответил
   (на израильской стороне), собрался только host-кандидат → соединение обречено.
   Повторная попытка сразу же сработала. Ретрай — штатная стратегия.
2. UI молчит, если srflx-кандидат не собран — пользователь тратит полный цикл
   обмена кодами впустую.
3. Offer/answer-коды протухают: обмен нужно делать быстро, без пауз в десятки минут.
4. Пара Израиль↔Россия прямым UDP пробилась, но со стороны РФ возможны
   деградация STUN Google и DPI-блокировки — TURN держим как запасной план.
5. **Живой тест с другом: заработало в Chrome, не заработало в Firefox**
   (соединение не установилось, канал не открылся). Скорее всего тот же
   сценарий, что и в п.1 — Firefox исторически медленнее собирает
   srflx-кандидат через STUN, а жёсткий таймаут в 3с (см. `waitForIce`)
   мог обрезать сбор раньше, чем STUN успел ответить → в SDP остались
   только host-кандидаты → соединение обречено за пределами одной LAN.
   Не подтверждено логами/webrtc-internals с той сессии — при следующем
   тесте стоит проверить `about:webrtc` в Firefox.

## Следующие шаги (по приоритету)

1. **Несколько STUN-серверов** в `RTC_CONFIG` (Cloudflare `stun:stun.cloudflare.com:3478`
   и 1–2 запасных) — параллельный опрос резко снижает долю сбоев сбора.
   Заодно поднять таймаут в `waitForIce` (сейчас 3с) — вероятная причина
   провала в Firefox (см. «Известные проблемы» п.5), там сбор STUN обычно
   медленнее, чем в Chrome.
2. **Индикатор srflx в UI:** после сбора проверить наличие `typ srflx` в
   `localDescription.sdp`; если нет — предупреждение «внешний адрес не получен,
   пересоздайте приглашение» до отправки кода, плюс кнопка «Пересоздать код»
   в самой карточке (не заставлять начинать с нуля).
3. **Индикатор пути после соединения:** показать выбранную пару кандидатов
   (direct/relay) через `pc.getStats()` — мини-диагностика без webrtc-internals.
4. **TURN fallback (по необходимости):** coturn на Vultr Stockholm VPS
   (там уже Docker + 3X-UI; порт 3478 udp/tcp + диапазон 49152–65535/udp,
   не конфликтует с Reality на 443). В конфиг добавить `turn:` с
   `?transport=udp` и `?transport=tcp`. Для отладки — `iceTransportPolicy: "relay"`.
5. **Децентрализованное представление новичков:** первое соединение вручную,
   дальше существующие пиры пересылают offer/answer новичку по открытым
   DataChannel — убирает квадратичный копипаст без ввода сервера.
6. Для игры: автоматический ICE restart / повторное рукопожатие как штатный
   механизм; в отчёты об ошибках включать состояние ICE обеих сторон.
7. **Таймстемп в чате:** показывать время у каждого сообщения (и текстового,
   и файлового) — сейчас в UI его нет.

## Грабли (чтобы не наступить снова)

- `createDataChannel` строго **до** `createOffer`.
- WebRTC требует secure context: HTTPS или `http://localhost` (не `file://`,
  не `http://192.168.x.x`).
- Glare при автоматизации сигналинга: в каждой паре детерминированно выбирать
  инициатора (например, по меньшему ID).
- Mesh масштабируется до ~5–6 участников, дальше — пересмотр архитектуры (SFU).
